# Post Publisher — Публікація постів

Веб-застосунок для публікації, редагування та управління постами.  
Фронтенд написаний на **TypeScript** і спілкується з Express-бекендом через REST API.

---

## Стек

| Частина | Технологія |
|---------|-----------|
| Фронтенд | TypeScript (ES2020), Vanilla DOM |
| Бекенд | Express 5, TypeScript, better-sqlite3 |
| Компілятор | `tsc` (без бандлера) |

---

## Як запустити проєкт

### 1. Бекенд

```bash
cd lr2-api-ts
npm install
npm run dev        # запуск на http://localhost:3000
```

Бекенд автоматично ініціалізує базу даних SQLite і застосовує міграції.  
Щоб наповнити базу тестовими даними:

```bash
npm run seed
```

### 2. Фронтенд

Спершу зкомпілюйте TypeScript:

```bash
# в кореневій теці проєкту (Lab1/)
npm install
npm run build      # tsc → dist/
```

Потім відкрийте `index.html` через **Live Server** у VS Code  
(розширення `ritwickdey.LiveServer`, порт 5500):

```
http://127.0.0.1:5500/index.html
```

Або через будь-який інший локальний веб-сервер.  
> **Важливо:** відкривати через `file://` не можна — браузер блокує `type="module"` скрипти без HTTP.

## Тестові сценарії

### Сценарій 1 — GET: список постів

1. Запустіть бекенд (`npm run dev` в `lr2-api-ts/`).
2. Відкрийте `http://127.0.0.1:5500/index.html`.
3. **Очікуваний результат:** таблиця заповнена постами; видно пагінацію і кількість елементів.
4. Клік на заголовок колонки — список сортується; кнопки «Попередня»/«Наступна» працюють.

### Сценарій 2 — POST: створення поста

1. Оберіть користувача зі списку (поле «Автор» підставиться автоматично).
2. Заповніть «Заголовок», «Категорія», «Текст».
3. Натисніть **Зберегти**.
4. **Очікуваний результат:** зелений банер «✅ Пост створено», таблиця оновлюється, форма очищується.

### Сценарій 3 — PUT: редагування поста

1. У рядку таблиці натисніть **Редагувати** — форма заповнюється даними поста.
2. Змініть будь-яке поле й натисніть **Зберегти**.
3. **Очікуваний результат:** банер «✅ Пост оновлено», рядок у таблиці оновлюється.

### Сценарій 4 — DELETE: видалення поста

1. Натисніть **Видалити** у рядку таблиці → підтвердіть у діалозі.
2. **Очікуваний результат:** банер «🗑️ Пост видалено», рядок зникає з таблиці.

### Сценарій 5 — Валідація 400

1. Залиште поле «Заголовок» порожнім і натисніть **Зберегти**.
2. **Очікуваний результат:** під полем з'являється повідомлення «Поле обов'язкове»; запит до сервера не надсилається.
3. Якщо надіслати невалідний запит напряму через `curl` — бекенд поверне `400 VALIDATION_ERROR` з масивом `details`.

### Сценарій 6 — Помилка мережі / бекенд недоступний

1. Зупиніть бекенд (Ctrl+C).
2. Перезавантажте сторінку або натисніть будь-яку кнопку, що робить запит.
3. **Очікуваний результат:** у таблиці замість рядків — повідомлення  
   `❌ Не вдалося з'єднатися з сервером. Перевірте, чи запущений бекенд.`  
   Форма залишається робочою.

### Сценарій 7 — Перевірка CORS

```bash
# Запит з дозволеного origin — має повернути дані
curl -H "Origin: http://127.0.0.1:5500" http://localhost:3000/api/v1/posts

# Запит з недозволеного origin — сервер поверне CORS-помилку
curl -H "Origin: http://evil.example.com" http://localhost:3000/api/v1/posts
```

## Правила DTO-контракту (don't-break-format)

1. **Ніколи не видаляти існуючі поля** зі відповіді — клієнт може на них покладатися.  
   Наприклад, `PostDto.id`, `PostDto.author`, `PostDto.createdAt` повинні завжди бути присутні.

2. **Ніколи не змінювати тип поля без версії** — якщо `id` зараз `string`, зміна на `number` ламає клієнта.  
   Нова поведінка вводиться через нову версію API (`/api/v2/...`).

3. **Коди помилок залишаються стабільними** — фронтенд перекладає `NETWORK_ERROR`, `TIMEOUT`, `NOT_FOUND`, `VALIDATION_ERROR`, `CONFLICT`, `INTERNAL_ERROR` у читабельні рядки.  
   Додавання нових кодів допускається; перейменування або видалення старих — ні.

```
├── tsconfig.json

    └── src/
        ├── index.ts    # Точка входу, CORS whitelist, маршрути /api/v1/…
        └── ...
```
